# 共享权重驱动的计算子图选择算法

采用“动态共享权重贪心 + 局部分支试算”。每轮优先考虑能被更多目标同时使用的数据节点；若试选削弱其他节点的共享机会，则从同一状态分别试选这些候选，各自继续普通贪心，比较所得完整子图。只提交胜出分支的第一个选择，然后重新评估。

输出是逻辑执行子图。中间节点是否物化，仍由后续增量代价评估决定。本算法是启发式，不保证全局最优或实际运行时间最短。

## 1. 输入、输出与状态

输入为候选图 G、基表集合 B、目标结果集合 T，及固定的节点/视图排序。示例使用 F、J23、G、J123、MV3 的顺序打破同权平局。

每个生产方式记录为 e = (Inputs, Output, Operation)。Inputs 是同时必需的全部输入。例如 {G, J23} → MV1 是一个完整生产方式；不能只保留 G → MV1。一个结果可以有多个候选生产方式，最终只能选一个。多个增量项若需合并，应建模为需要全部增量项的合并生产方式。

算法维护：

| 状态 | 含义 |
|---|---|
| Req[t] | 目标 t 的最终生产方案必须包含的数据节点集合 |
| Selected | 已提交的共享节点，不再进入待选队列 |
| U[v] | 分别存在合法方案可使用 v 的目标集合 |
| C[v] | U[v] 中人数最多、能同时使用 v 的一个目标子集 |
| w[v] | 有效共享权重，等于 |C[v]| |
| P_safe | 一份满足当前 Req 的完整无环方案，作为可执行依据 |

选择 v 的含义是：对 t ∈ C[v]，执行 Req[t] ← Req[t] ∪ {v}。只要求这些目标使用 v，暂不锁定它们的完整生产路径。

若 U[v] 中所有目标能同时使用 v，则 C[v] = U[v]。前面的 F、J23、G、J123、MV3 示例均属于这种情况。共同可行性检查用于处理环路或共享生产方式冲突，避免“分别可用”被误认为“可以一起使用”。同样大小的可行 C 按固定视图顺序择一，是本启发式的确定性取舍。

完整生产方案中的 Ancestors(P, t) 包含 t 自身，以及沿选中生产方式递归展开的全部输入。间接使用也计入共享，同一目标对一个节点只贡献一次。

## 2. 合法方案搜索：FindPlan

FindPlan(Req) 返回一份满足要求的完整无环方案，或在穷尽搜索后返回 FAIL。它按需回溯生产方式，不预先枚举全部完整计划。

搜索维护 Prod[v]（已经为 v 选择的生产方式）和 Open（已需要、但还未决定生产方式的非基表节点）。初始 Open 仅包含目标，不能把共享候选直接塞入 Open；否则可能生成与目标无关的节点。

```text
function FindPlan(Req):
    return Search(Prod = {}, Open = T - B)

function Search(Prod, Open):
    if Open is empty:
        for each target t in T:
            if Req[t] is not a subset of Ancestors(Prod, t):
                return FAIL
        return Prod

    v = node in Open with fewest candidate producers
        // 同数时按固定节点顺序；这里只决定回溯效率

    for each production e of v in fixed order:
        Trial = copy(Prod)
        Trial[v] = e

        if HasCycle(Trial):
            continue

        NextOpen = (Open union Inputs(e)) - B - Keys(Trial)
        P = Search(Trial, NextOpen)
        if P != FAIL:
            return P

    return FAIL
```

其中：

- Ancestors 从目标出发，用集合去重，反复加入所选生产方式的全部输入，直到没有新节点。
- HasCycle 将已选生产方式的每个输入 u → 输出 v 展开为依赖弧，用入度队列执行拓扑排序。无法输出全部涉及节点即有环；全部输入仍由生产方式整体记录，不能独立选择。
- 一个数据节点只有一个 Prod[v]，不同目标复用同一个生产方式。只有新节点进入 Open，因此搜索深度不超过非基表节点数。
- 环检测针对 Trial 的已选依赖，不能针对保留全部替代路径的 G。
- 当前分支失败后，撤回的是本次生产方式组合，其他方式仍可尝试。每个递归层均使用独立状态副本。

这个搜索同时落实：所有目标完整生成、全部输入齐全、共享生产方式一致、已选依赖无环、Req 得到满足。它返回第一份合法方案，并不在此处声称找到最优生产方案。

## 3. 更新消费者和权重：Prepare

先逐个目标检查 v 能否被使用，获得潜在集合 U；再验证所有目标能否共同使用 v。共同使用失败时，按人数从多到少尝试目标子集，取第一个合法集合。人数小于 2 的节点不作为共享选择候选，但仍允许出现在最终计算路径中。

```text
function Bind(Req, v, Consumers):
    R = deep_copy(Req)
    for each t in Consumers:
        R[t] = R[t] union {v}
    return R

function Prepare(Req, Selected):
    Info = {}
    for each non-base node v not in Selected:
        U = {}
        for each target t in T:
            if FindPlan(Bind(Req, v, {t})) != FAIL:
                U = U union {t}

        for size = |U| down to 2:
            for each size-element subset C of U in fixed order:
                R = Bind(Req, v, C)
                P = FindPlan(R)
                if P != FAIL:
                    Info[v] = (U, C, weight = |C|, R, P)
                    go to the next node v

    return Info
```

通常整个 U 就能通过校验，不需要尝试较小子集。每个候选记录可提交的约束 R 和完整方案 P，试选时直接使用。新状态的约束只增加，共享机会只会保持或收缩。

## 4. 分支评分

对完整图 P，定义：

\[
r_P(v)=|\{t\in T: v\in Ancestors(P,t)\}|,
\qquad
R(P)=\sum_{v\in V(P)\setminus B}\max(r_P(v)-1,0).
\]

第一次使用不是共享，此后每多服务一个目标贡献 1。目标节点也可以共享，例如 MV3 既是目标又用于生成 MV4，贡献 1。

分支先比较 R(P)，相同时优先选择生产方式数量更少的图，再按固定顺序打破平局。可以写成 Score(P) = (R(P), -|Prod(P)|)，按字典序最大化。

这是统一图粒度下的结构共享评分，不是实际节省的算子次数或运行时间。物化收益仍由后续代价模型评估。

## 5. 普通贪心续选：Rollout

试算时先提交指定候选，再不断选择有效权重最高的剩余候选；每次重算消费者和权重。续选内部不再递归开展分支比较，避免形成多层组合搜索。

```text
function Rollout(Req, Selected, first, Info):
    R = Info[first].R
    S = Selected union {first}
    P = Info[first].P

    while true:
        I = Prepare(R, S)
        if I is empty:
            return P

        v = highest-weight node in I, ties by fixed order
        R = I[v].R
        P = I[v].P
        S = S union {v}
```

## 6. 主算法

本轮先试选权重最高的 x，找出因此失去潜在消费者、有效权重下降或不再能共享的节点，作为局部比较对象。无需预先构造冲突图，也无需按拓扑层分组。

设 L 为每轮最多比较的起始候选数，示例取 L = 3。必须包含 x，其余从受影响候选中按原权重选择。

```text
function SelectSubgraph(G, B, T, L = 3):
    Req[t] = {} for every target t
    Selected = {}
    P_safe = FindPlan(Req)
    if P_safe == FAIL:
        return "候选图缺少合法的完整生产方案"

    while true:
        Before = Prepare(Req, Selected)
        if Before is empty:
            return ReversePrune(P_safe, T)

        x = highest-weight node in Before, ties by fixed order
        After = Prepare(Before[x].R, Selected union {x})

        Affected = {}
        for each u in Before except x:
            if u is absent from After
               or Before[u].U - After[u].U is not empty
               or After[u].weight < Before[u].weight:
                add u to Affected

        winner = x
        P_trial = Before[x].P

        if Affected is not empty:
            Options = [x] + top (L-1) affected nodes by old weight
            best_score = (-infinity, -infinity)

            for each z in Options:
                // 每个分支从同一 Req、Selected 出发
                Q = Rollout(Req, Selected, z, Before)
                if Score(Q) > best_score:
                    best_score = Score(Q)
                    winner = z
                    P_trial = Q

        Req = Before[winner].R
        Selected = Selected union {winner}
        P_safe = P_trial
        // 只提交胜出分支的第一个选择，试算中的其他约束不提交
```

ReversePrune 从所有目标沿选中生产方式反向追溯，保留祖先闭包及对应计算，删除未被使用的候选节点和替代边。FindPlan 本身只展开目标依赖，已不会主动引入无用计算；最后剪枝用于兼容工程上以合并/替换方式维护的图。

P_safe 可以含有试算中使用的其他节点，但它们尚未加入 Req，所以后续仍能换成其他合法路径。所有正式选择都拥有一个完整可执行依据。

## 7. 当前示例

假设候选改写语义合法。G 维护满足连接及 AVG 改写要求的分组键、SUM 和非空 COUNT，连接保留原查询的重复度语义。

| 正式提交后的状态 | F | J23 | G | J123 | MV3 |
|---|---:|---:|---:|---:|---:|
| 初始 | 3 | 3 | 2 | 2 | 2 |
| 选 F | 3 | 3 | 2 | 2 | 2 |
| 选 J23 | 3 | 3 | 2 | 2 | 2 |
| 比较后选 G | 3 | 3 | 2 | 1 | 2 |
| 选 MV3 | 3 | 3 | 2 | 0 | 2 |

F 和 J23 同权，固定顺序先 F。选择它们不削弱其他候选，直接提交。

试选 G 后，J123 失去 MV1，权重 2 → 1，因此比较两个分支：

- 先 G：随后贪心选 MV3。F、J23 各贡献 2，G、MV3 各贡献 1，R = 6。
- 先 J123：G 仅服务 MV2，MV3 仅服务自身，没有新的共享候选。F、J23 各贡献 2，J123 贡献 1，R = 5。

正式提交 G，下一轮再提交 MV3。最终为：

```text
t1          --过滤----------> F
F           --按连接键分组--> G
t2 + t3     --连接----------> J23

G + J23     --连接并汇总----> MV1
G           --汇总并求 AVG-> MV2
J23 + t4    --连接----------> MV3
F + MV3     --连接----------> MV4
```

J123 没有任何实际消费者，被移除。

## 8. 环路、边界与落地

候选图可以同时保留 ABC + D → ABCD 与 ABCD → ABC。最终允许从基表生成 ABC 再生成 ABCD，或直接生成 ABCD 再投影 ABC；禁止把两种互相等待的生产方式同时选中。每次添加生产方式后执行的拓扑检查覆盖此类问题。

若环来自读取上一轮物化状态，应区分旧状态与本轮输出的数据版本，不能将跨轮状态依赖误当成本轮循环。本文不处理需要固定点执行的递归查询。

外层正式选择至多提交一次每个非基表节点；一次 Rollout 也至多如此。单次环检测为 O(V+E)（E 为展开后的依赖弧数）。但 FindPlan 的生产方式回溯及共同消费者子集搜索最坏具有指数级开销，不能将整个算法宣称为线性或多项式时间。

第一版可以直接实现以上完整搜索，用于小规模候选图。规模扩大时优先缓存 (Req, G版本) → 完整方案/确切失败，复用仍满足新 Req 的方案，以及为本轮受影响节点增量更新权重。L 限制外层分支数，不会消除内部合法性搜索的组合开销。

若增加搜索预算，搜索结果必须区分 FOUND、INFEASIBLE、UNKNOWN。只有穷尽搜索才能判定 INFEASIBLE；超时不能据此删减消费者或把权重置零。最简单的安全处理是结束本轮，返回已验证的 P_safe。

原示例、双向依赖含环示例、潜在消费者不能共同使用同一节点的反例，已通过配套 Python 验证脚本。脚本用于验证算法逻辑，尚未接入数据库优化器、SQL 等价性证明及真实成本模型。

下面以[完整算法方案](<D:/公司/华为实习-增量计算/方案提交/output/共享权重驱动计算子图选择_完整算法.md>)中的伪代码为准，**每行编号、逐行解释**。不再重复算法思想，重点解释“这行操作了什么、为什么这样写、执行后状态如何变化”。

为避免混淆，做两处记号调整：

- 候选图写成 `Graph`；示例中的聚合节点仍叫 `G`。
- `Search` 显式接收 `Req`。原版隐含读取外层的 `Req`，不够直观。

以下行号只供解释，不属于代码。

**一、先统一变量和基本写法**

| 名称 | 保存的内容 |
|---|---|
| `Graph` | 包含所有候选生产方式的计算图 |
| `B` | 基表节点集合，如 `{t1,t2,t3,t4}` |
| `T` | 目标节点集合，如 `{MV1,MV2,MV3,MV4}` |
| `Req[t]` | 目标 `t` 必须经过哪些数据节点 |
| `Selected` | 已经正式选中的共享节点 |
| `Prod[v]` | 当前为数据节点 `v` 选择的生产方式 |
| `Open` | 已经需要、但还没确定生产方式的非基表节点 |
| `Info[v]` | 关于候选节点 `v` 的一行记录 |
| `P` | 一份完整执行方案，主要由生产方式表 `Prod` 表示 |
| `FAIL` | 在当前要求下，没有找到合法方案；本文指穷尽搜索后失败 |

这里的“生产方式”是一个完整操作。例如：

```text
e = {G, J23} → MV1
```

表示计算 `MV1` **同时需要** `G` 和 `J23`。

一些基础写法：

| 写法 | 含义 |
|---|---|
| `A ∪ B` | 合并集合，重复元素只保留一个 |
| `A - B` | 从 A 中删除属于 B 的元素 |
| `|A|` | A 的元素数量 |
| `Keys(Prod)` | 已经存在于 `Prod` 左侧的节点，即已确定生产方式的节点 |
| `Info[v].R` | 读取候选表中，节点 v 所在行的 R 字段 |
| `return X` | 当前函数结束，把 X 交给调用者 |
| `continue` | 跳过当前尝试，继续当前循环的下一次尝试 |

`Graph、B、T` 是固定输入，下面各函数都可以读取它们。

---

**二、`Bind`：添加一项“必须经过某节点”的要求**

先解释这个最简单的函数，因为后面多次用到它。

```text
01 function Bind(Req, v, Consumers):
02     R = deep_copy(Req)
03     for each t in Consumers:
04         R[t] = R[t] ∪ {v}
05     return R
```

| 行号 | 逐行解释 |
|---|---|
| 01 | 定义函数。输入当前要求 `Req`、准备选择的节点 `v`，以及准备让它服务的目标集合 `Consumers`。 |
| 02 | 完整复制当前要求，得到临时要求 `R`。之后修改 `R`，不会影响正式的 `Req`。 |
| 03 | 依次处理准备使用节点 v 的每个目标。 |
| 04 | 在该目标的要求中加入 v。集合会去重，已经有 v 就不重复添加。 |
| 05 | 返回修改后的要求。这里只返回一个备选状态，尚未正式提交。 |

例如，原来：

```text
Req[MV1] = {F, J23}
Req[MV2] = {F}
```

执行：

```text
Bind(Req, G, {MV1, MV2})
```

返回：

```text
R[MV1] = {F, J23, G}
R[MV2] = {F, G}
```

原来的 `Req` 保持不变。

**这个函数不搜索路径，也不判断合法性。它只负责修改要求清单。**

---

**三、`FindPlan` 和 `Search`：寻找满足要求的完整执行方案**

代码如下：

```text
01 function FindPlan(Req):
02     return Search(Req, Prod = {}, Open = T - B)

03 function Search(Req, Prod, Open):
04     if Open is empty:
05         for each target t in T:
06             if Req[t] is not a subset of Ancestors(Prod, t):
07                 return FAIL
08         return Prod

09     v = node in Open with fewest candidate producers

10     for each production e of v in fixed order:
11         Trial = copy(Prod)
12         Trial[v] = e

13         if HasCycle(Trial):
14             continue

15         NextOpen = (Open ∪ Inputs(e)) - B - Keys(Trial)
16         P = Search(Req, Trial, NextOpen)
17         if P != FAIL:
18             return P

19     return FAIL
```

先看入口：

| 行号 | 逐行解释 |
|---|---|
| 01 | `FindPlan` 接收一份要求，任务是找出一张满足要求的完整执行图。 |
| 02 | 启动搜索。`Prod={}` 表示尚未确定任何生产方式；`Open=T-B` 表示先处理所有非基表目标。最后把搜索结果直接返回。 |
| 03 | 定义真正进行搜索的函数。`Req` 是要求，`Prod` 是已决定的生产方式，`Open` 是尚待处理的节点。 |

例如最开始：

```text
Prod = {}

Open = {MV1, MV2, MV3, MV4}
```

注意，**初始 `Open` 不是所有候选节点**。只有目标需要某个输入时，才把该输入加入待处理集合。否则可能主动生成无用节点。

接下来检查是否已经补全：

| 行号 | 逐行解释 |
|---|---|
| 04 | 如果 `Open` 为空，说明目前需要的所有非基表节点，都已经确定了生产方式。 |
| 05 | 逐个检查目标。生产方式完整，还不代表一定满足“必须经过哪些节点”的要求。 |
| 06 | 计算目标 t 的全部实际依赖节点，检查是否包含 `Req[t]` 中的每个要求。`Ancestors` 包含 t 自身。 |
| 07 | 只要一个目标缺少某个必经节点，当前方案就不合格，返回失败。 |
| 08 | 所有目标都满足要求，返回当前生产方式表。此时它已经代表一份完整合法方案。 |

例如：

```text
Req[MV1] = {F, J23, G}
```

但实际选出的路径是：

```text
F + J23 → J123 → MV1
```

那么 `Ancestors(Prod,MV1)` 不包含 `G`，第 06 行检查失败，执行第 07 行。

接下来是“尚未补全时怎么办”：

| 行号 | 逐行解释 |
|---|---|
| 09 | 从待处理节点中，取一个候选生产方式最少的节点。这里是在决定搜索顺序，不是在决定共享优先级。数量相同时按固定顺序。 |
| 10 | 依次尝试这个节点的每一种生产方式。 |
| 11 | 复制当前生产方式表，得到本次尝试使用的 `Trial`。这样本次失败时，不会破坏原来的 `Prod`。 |
| 12 | 在 `Trial` 中记录：节点 v 本次使用生产方式 e。 |
| 13 | 检查这次增加的生产方式是否让已选依赖形成环。 |
| 14 | 如果有环，放弃本次 e，回到第 10 行尝试 v 的下一种生产方式。 |

第 09 行容易混淆：

```text
选择候选生产方式最少的节点
```

不是在说共享节点应该按这个顺序选。它只是 `FindPlan` 内部补全图的顺序。**外层共享选择仍然按权重进行。**

然后更新待办集合，并继续搜索：

| 行号 | 逐行解释 |
|---|---|
| 15 | 更新待处理节点：加入新生产方式的全部输入，去掉基表，再去掉已经确定生产方式的节点。 |
| 16 | 递归调用 `Search`，在当前尝试的基础上继续补全剩余节点。 |
| 17 | 检查后续是否成功补全。 |
| 18 | 如果成功，直接把完整方案返回，不再尝试其他生产方式。 |
| 19 | 当前节点的全部生产方式都尝试失败，才执行这一行，向上一层返回失败。 |

第 15 行可以拆开看：

```text
NextOpen = (Open ∪ Inputs(e)) - B - Keys(Trial)
```

假设：

```text
Open = {MV1, MV2}
本次选择：{G, J23} → MV1
```

变化过程是：

```text
加入输入：
{MV1, MV2, G, J23}

去掉基表：
这里没有基表，集合不变

去掉已确定生产方式的 MV1：
{MV2, G, J23}
```

所以：

```text
NextOpen = {MV2, G, J23}
```

第 16～19 行体现的是**回退**：

```text
尝试 MV1 的方式一
    后续补全失败
回到当前这一层
尝试 MV1 的方式二
    后续补全成功
返回完整方案
```

`FAIL` 通常只是当前搜索分支失败，不代表主算法立刻结束。

**四、`Prepare`：生成当前候选表**

这段代码负责给每个候选节点统计消费者、检查共同可行性、保存权重和备选方案。

```text
01 function Prepare(Req, Selected):
02     Info = {}

03     for each non-base node v not in Selected:
04         U = {}

05         for each target t in T:
06             if FindPlan(Bind(Req, v, {t})) != FAIL:
07                 U = U ∪ {t}

08         for size = |U| down to 2:
09             for each size-element subset C of U in fixed order:
10                 R = Bind(Req, v, C)
11                 P = FindPlan(R)

12                 if P != FAIL:
13                     Info[v] = (U, C, weight = |C|, R, P)
14                     go to the next node v

15     return Info
```

先解释找潜在消费者的部分：

| 行号 | 逐行解释 |
|---|---|
| 01 | 输入当前要求和已经正式选择过的共享节点。 |
| 02 | 创建空候选表。之后每个值得考虑的共享节点占一行。 |
| 03 | 遍历候选图中的非基表节点，但跳过已经在 `Selected` 中的节点，避免重复选择。目标结果节点也可以参与，例如 `MV3`。 |
| 04 | 为当前节点 v 创建空的潜在消费者集合 U。每处理一个新节点，都重新创建。 |
| 05 | 逐个考察目标 t。 |
| 06 | 临时增加“目标 t 必须使用 v”的要求，然后寻找完整合法方案。如果找得到，说明在当前状态下 t 可以使用 v。 |
| 07 | 将这个目标加入 U。集合保证同一目标只计一次。 |

第 06 行是两个函数嵌套，执行顺序是**从里面到外面**：

```text
FindPlan(Bind(Req, v, {t}))
```

等价于：

```text
临时要求 = Bind(Req, v, {t})
临时方案 = FindPlan(临时要求)

检查临时方案是否失败
```

例如：

```text
v = G
t = MV1
```

实际检查的是：

> 在已有要求不变的情况下，再要求 MV1 使用 G，是否还能生成全部目标？

这里找的是完整图，不是只检查 `G` 能否沿某条边到达 `MV1`。

接下来检查这些目标能否共同使用 v：

| 行号 | 逐行解释 |
|---|---|
| 08 | 先尝试让 v 服务全部潜在消费者；失败后，再尝试少一个、少两个，直到人数为 2。 |
| 09 | 枚举当前人数下的目标子集 C。人数相同时按固定顺序尝试。 |
| 10 | 增加“C 中每个目标都必须使用 v”的要求，得到 R。 |
| 11 | 搜索是否存在一份同时满足这些要求的完整图。 |
| 12 | 如果存在，说明这些目标能够共同使用 v。 |
| 13 | 将当前节点的一行信息存入候选表：潜在消费者 U、共同消费者 C、权重、试选后要求 R、完整方案 P。 |
| 14 | 当前节点已经找到最多人数的可行组合，停止为它继续找更小组合，转去处理第 03 行的下一个节点。 |
| 15 | 所有节点处理完毕后，返回整张候选表。 |

**第 14 行不是普通的 `continue`。**

它的意思是：

```text
跳出“人数循环”和“子集循环”
回到第 03 行，处理下一个节点
```

如果只跳过第 09 行的当前子集，就不是这里想表达的行为。

例如：

```text
U = {MV1, MV2, MV4}
```

尝试顺序可以是：

```text
先试 3 个：
{MV1, MV2, MV4}

如果不合法，再试 2 个：
{MV1, MV2}
{MV1, MV4}
{MV2, MV4}
```

假设第一组两人集合合法，就记录：

```text
C = {MV1, MV2}
weight = 2
```

然后处理下一个节点。

若最多只能服务一个目标，就不会写入 `Info`。这只表示它不再是共享选择候选，**不是从计算图中删除它**。

**五、`Score`：如何计算一份完整图的分数**

原方案用公式表示，这里将它展开成等价伪代码：

```text
01 function Score(P):
02     sharing_score = 0

03     for each non-base node v in P:
04         users = {t in T | v belongs to Ancestors(P, t)}
05         sharing_score = sharing_score + max(|users| - 1, 0)

06     producer_count = number of selected production rules in P
07     return (sharing_score, -producer_count)
```

| 行号 | 逐行解释 |
|---|---|
| 01 | 输入一份完整执行图，计算它的比较分数。 |
| 02 | 共享评分初始化为 0。 |
| 03 | 逐个查看图中的非基表节点。包括中间节点，也包括目标节点。 |
| 04 | 找出最终实际使用 v 的目标集合。间接使用也算，因为检查的是全部祖先依赖。 |
| 05 | 第一个使用者不计共享，之后每增加一个使用者加 1 分。 |
| 06 | 统计完整图中选了多少个生产方式。 |
| 07 | 返回两个数：先比较共享评分；评分相同时，比较生产方式数量，越少越好。 |

第 07 行为什么写负号？

例如：

```text
方案 A：共享评分 6，生产方式 7 个
Score(A) = (6, -7)

方案 B：共享评分 6，生产方式 9 个
Score(B) = (6, -9)
```

先比较第一项，都是 6；再比较第二项：

```text
-7 > -9
```

所以 A 胜出。

原示例中：

```text
先 G 的结果：共享评分 6
先 J123 的结果：共享评分 5
```

第一项已经分出胜负，无需比较第二项。

这里统计的是**完整图中的实际使用关系**，不是 `Prepare` 中尚未实现的潜在权重。

**六、`Rollout`：从一个指定节点出发，进行临时贪心续选**

```text
01 function Rollout(Req, Selected, first, Info):
02     R = Info[first].R
03     S = Selected ∪ {first}
04     P = Info[first].P

05     while true:
06         I = Prepare(R, S)
07         if I is empty:
08             return P

09         v = highest-weight node in I, ties by fixed order
10         R = I[v].R
11         P = I[v].P
12         S = S ∪ {v}
```

初始化部分：

| 行号 | 逐行解释 |
|---|---|
| 01 | 输入本轮正式状态、准备试选的起点 `first`、以及试选前候选表 `Info`。 |
| 02 | 从候选表中取出“选择 first 后的要求”，作为本次试算的临时要求 R。 |
| 03 | 创建临时已选集合 S：原来已选的节点，再加上 first。 |
| 04 | 取出候选表中已经为 first 找到的合法完整图，作为临时方案 P。 |

例如：

```text
first = G
```

第 02～04 行表示：

```text
临时要求：在原要求上，让 MV1、MV2 使用 G
临时已选：{F, J23, G}
临时方案：一份满足上述要求的完整图
```

循环部分：

| 行号 | 逐行解释 |
|---|---|
| 05 | 不断重复下面的续选过程，直到第 08 行返回。 |
| 06 | 根据当前临时要求 R 和临时已选集合 S，重新生成候选表 I。 |
| 07 | 检查是否已经没有新的共享候选。 |
| 08 | 如果没有，就结束本次试算，返回当前完整图 P。 |
| 09 | 如果还有候选，取有效权重最高的节点 v；同权时按固定顺序。 |
| 10 | 将临时要求更新为选择 v 后的要求。注意，这份新要求已经包含之前的要求。 |
| 11 | 将临时方案更新为满足新要求的完整图。 |
| 12 | 把 v 加入临时已选集合，避免下一轮重复选择它。随后回到第 05 行。 |

在“先选 G”的分支中：

```text
第 06 行得到：MV3=2，J123 不再是共享候选
第 09 行选择：MV3
第 10 行增加：MV4 必须使用 MV3
第 12 行得到：S={F,J23,G,MV3}

下一次第 06 行：没有新候选
第 08 行：返回完整图
```

这个函数内部没有再次调用“分支比较”。它只是一路按权重贪心。

还有一个容易困惑的地方：第 01 行传入了 `Req`，正文却没有再直接使用它。原因是 `Info[first].R` 已经包含“原 Req 加上 first 的要求”。**这个参数在当前写法里可以省略；保留它只是为了表明试算对应哪个起始状态。**

**七、`SelectSubgraph`：完整主程序逐行解释**

```text
01 function SelectSubgraph(Graph, B, T, L = 3):
02     Req[t] = {} for every target t
03     Selected = {}
04     P_safe = FindPlan(Req)
05     if P_safe == FAIL:
06         return "候选图缺少合法的完整生产方案"

07     while true:
08         Before = Prepare(Req, Selected)
09         if Before is empty:
10             return ReversePrune(P_safe, T)

11         x = highest-weight node in Before, ties by fixed order
12         After = Prepare(Before[x].R, Selected ∪ {x})

13         Affected = {}
14         for each u in Before except x:
15             if u is absent from After
16                or Before[u].U - After[u].U is not empty
17                or After[u].weight < Before[u].weight:
18                 add u to Affected

19         winner = x
20         P_trial = Before[x].P

21         if Affected is not empty:
22             Options = [x] + top (L-1) affected nodes by old weight
23             best_score = (-infinity, -infinity)

24             for each z in Options:
25                 Q = Rollout(Req, Selected, z, Before)
26                 if Score(Q) > best_score:
27                     best_score = Score(Q)
28                     winner = z
29                     P_trial = Q

30         Req = Before[winner].R
31         Selected = Selected ∪ {winner}
32         P_safe = P_trial
```

先看初始化：

| 行号 | 逐行解释 |
|---|---|
| 01 | 主算法入口。`L=3` 表示每轮最多比较 3 个不同起点，不是只看 3 个节点，也不是续选只执行 3 步。 |
| 02 | 每个目标的额外要求都初始化为空。目前只要求目标能被完整生成，没有指定共享节点。 |
| 03 | 已正式选择的共享节点为空。 |
| 04 | 先寻找一份完整合法方案，存入 `P_safe`。这样后续选择始终有可执行方案作为依据。 |
| 05 | 检查初始候选图是否就无法生成全部目标。 |
| 06 | 如果无法生成，直接返回错误。共享优化不能弥补候选图本身缺少合法生产方案的问题。 |

进入每轮决策：

| 行号 | 逐行解释 |
|---|---|
| 07 | 开始主循环，每轮正式选择一个共享节点。 |
| 08 | 根据当前正式要求和已选集合，生成本轮试选前候选表 `Before`。 |
| 09 | 检查是否已无新的共享候选。 |
| 10 | 如果没有，对当前合法图做最后剪枝，输出并结束。 |

`Before` 为空不表示图里没有节点，只表示：

```text
没有尚未正式选择、且还能共同服务至少两个目标的候选。
```

接下来先试最高权重节点：

| 行号 | 逐行解释 |
|---|---|
| 11 | 从本轮候选表中选权重最大的节点 x，作为首先考虑的节点。 |
| 12 | 使用“选择 x 后的要求”和“临时加入 x 的已选集合”，生成另一张候选表 `After`。这一步是试选，不修改正式的 `Req、Selected`。 |

假设：

```text
x = G
```

第 12 行：

```text
After = Prepare(Before[G].R, Selected ∪ {G})
```

可以拆成：

```text
临时要求 = Before[G].R
临时已选 = Selected ∪ {G}
After = Prepare(临时要求, 临时已选)
```

现在有两张表：

```text
Before：还没确定使用 G 时
After：假设已经确定使用 G 时
```

然后找受影响节点：

| 行号 | 逐行解释 |
|---|---|
| 13 | 创建空集合，用于记录被 x 削弱的其他候选。 |
| 14 | 逐个检查原候选表中的节点 u，但不检查 x 自己。 |
| 15 | 第一种受损情况：u 在试选后消失了。这通常意味着它已不能同时服务至少两个目标。 |
| 16 | 第二种受损情况：u 虽然仍存在，但失去了某些潜在消费者。集合差表示“原来有、现在没有”的目标。 |
| 17 | 第三种受损情况：u 的有效共同消费者数量下降。即使潜在集合不变，共同可行性也可能变差。 |
| 18 | 满足任意一种情况，就把 u 加入 `Affected`。 |

第 15～17 行按“或”连接。**如果第 15 行已经成立，就不需要再读取不存在的 `After[u]`。**

例如选择 G 后：

```text
Before[J123]：权重 2
After 中没有 J123 这一行
```

原因是它只剩一个消费者，不再进入候选表。因此第 15 行成立，将它加入 `Affected`。

也可能出现：

```text
原来权重 3
现在权重 2
```

这时节点还在表中，但第 17 行成立，同样需要比较。

接下来设置默认结果：

| 行号 | 逐行解释 |
|---|---|
| 19 | 暂时认为最初考虑的 x 会胜出。 |
| 20 | 暂时把 x 所在行保存的完整合法图作为本轮方案。 |

这两行的作用是处理“没有其他节点受损”的情况。

例如选择 F 后：

```text
Affected 为空
```

就不需要分支试算，直接采用默认的：

```text
winner = F
P_trial = 选择 F 后的一份合法完整图
```

如果存在受损候选，则开始比较：

| 行号 | 逐行解释 |
|---|---|
| 21 | 只有存在受影响节点时，才进入分支比较。 |
| 22 | 构造起点列表。一定包含 x，再加入原权重最高的最多 L−1 个受影响节点。 |
| 23 | 将当前最好分数设为负无穷，让第一个合法结果必然能更新它。 |
| 24 | 逐个以列表中的节点 z 作为试算起点。 |
| 25 | 从相同的正式状态 `Req、Selected` 出发，先选 z，再进行贪心续选，得到完整图 Q。 |
| 26 | 比较 Q 是否优于此前已经试算的结果。 |
| 27 | 如果更好，更新当前最好分数。 |
| 28 | 记录产生这个结果的起点节点 z。 |
| 29 | 保存该完整图 Q，作为本轮目前最好的结果。 |

第 22 行中的 `L` 举例：

```text
L = 3
x = G
受影响节点有 5 个
```

本轮只比较：

```text
G
原权重最高的受影响节点
原权重第二高的受影响节点
```

最多三个起点。每个起点内部仍然可以继续贪心选择多个节点。

第 25 行尤其重要：

```text
Q = Rollout(Req, Selected, z, Before)
```

每次传入的都是同一份本轮正式状态，而不是上一个分支留下的临时状态。

因此比较 G 和 J123 时：

```text
分支一：从 {F,J23} 出发，先 G
分支二：仍从 {F,J23} 出发，先 J123
```

不会变成：

```text
先选了 G，再评价 J123
```

最后正式提交：

| 行号 | 逐行解释 |
|---|---|
| 30 | 将正式要求更新为“胜出节点对应的新要求”。这里只提交胜出起点的要求。 |
| 31 | 将胜出节点加入正式已选集合。 |
| 32 | 保存本轮得到的完整合法图。随后回到第 07 行，进入下一轮。 |

假设胜出分支是：

```text
先 G，再 MV3
```

第 30～32 行的结果是：

```text
正式要求：增加 MV1、MV2 必须使用 G
正式已选：{F,J23,G}
备用完整图：可以已经使用 G 和 MV3
```

为什么正式已选没有立即加入 MV3？

因为 `MV3` 是试算续选得到的选择，本轮只正式提交起点 G。下一轮仍然可以重新评估 MV3。

**备用图使用了某个节点，不代表那个节点已经成为不可更改的正式要求。**

---

**八、三个辅助操作也展开说明**

原方案只描述了这三个辅助操作，没有给出完整代码。下面补成等价伪代码，避免关键逻辑藏在函数名里。

先看 `Ancestors`：

```text
01 function Ancestors(P, t):
02     Seen = {}
03     Pending = [t]

04     while Pending is not empty:
05         v = remove one node from Pending
06         if v belongs to Seen:
07             continue
08         add v to Seen

09         if P contains a production rule for v:
10             add all inputs of that rule to Pending

11     return Seen
```

| 行号 | 逐行解释 |
|---|---|
| 01 | 输入执行图 P 和目标 t，寻找 t 的全部依赖。 |
| 02 | `Seen` 记录已经访问过的节点，初始为空。 |
| 03 | 待访问列表先放入目标自身，所以最终结果包含 t。 |
| 04 | 只要还有待访问节点，就继续。 |
| 05 | 取出一个节点 v。 |
| 06 | 检查是否已经访问过。 |
| 07 | 已访问过就跳过，避免重复统计。 |
| 08 | 首次访问，将 v 加入结果集合。 |
| 09 | 检查 v 是否有选中的生产方式。基表一般没有。 |
| 10 | 如果有，把该生产方式的全部输入加入待访问列表。 |
| 11 | 全部追溯完成后，返回去重后的依赖集合。 |

例如：

```text
F + MV3 → MV4
J23 + t4 → MV3
t2 + t3 → J23
t1 → F
```

调用：

```text
Ancestors(P,MV4)
```

得到：

```text
{MV4,F,MV3,J23,t1,t2,t3,t4}
```

所以 MV4 间接使用 J23，也会被计入 J23 的实际消费者。

再看 `HasCycle`：

```text
01 function HasCycle(P):
02     D = expand selected rules into input-to-output dependency arcs
03     indegree[v] = number of incoming arcs of v in D
04     Ready = all nodes with indegree 0
05     processed = 0

06     while Ready is not empty:
07         u = remove one node from Ready
08         processed = processed + 1

09         for each arc u → v:
10             indegree[v] = indegree[v] - 1
11             if indegree[v] == 0:
12                 add v to Ready

13     return processed < number of nodes in D
```

| 行号 | 逐行解释 |
|---|---|
| 01 | 检查当前选中生产方式是否形成环。P 可以是尚未补全的部分图。 |
| 02 | 将生产方式展开成依赖弧。例如 `{G,J23}→MV1` 展开成 `G→MV1` 和 `J23→MV1`。这里只用于检测依赖，生产方式本身仍整体选择。 |
| 03 | 统计每个节点有多少个前置依赖。 |
| 04 | 将没有前置依赖的节点放入可处理集合。 |
| 05 | 已处理节点数初始化为 0。 |
| 06 | 不断处理当前没有前置依赖的节点。 |
| 07 | 取出一个可处理节点 u。 |
| 08 | 已处理数量加 1。 |
| 09 | 查看所有直接依赖 u 的节点 v。 |
| 10 | u 已处理，因此 v 尚未处理的前置依赖减少一个。 |
| 11 | 检查 v 的前置依赖是否全部处理完。 |
| 12 | 如果全部处理完，将 v 加入可处理集合。 |
| 13 | 如果最终仍有节点无法处理，就说明剩余节点互相等待，存在环，返回真。否则返回假。 |

例如：

```text
ABC → ABCD
ABCD → ABC
```

两个节点都有未满足的前置依赖，没有一个能先处理，因此检测到环。

这个检测只看**选中的生产方式**，不会因为候选图中保留反向替代边，就判定当前方案有环。

最后是 `ReversePrune`：

```text
01 function ReversePrune(P, T):
02     Keep = {}

03     for each target t in T:
04         Keep = Keep ∪ Ancestors(P, t)

05     return the nodes in Keep and their selected production rules
```

| 行号 | 逐行解释 |
|---|---|
| 01 | 输入准备输出的执行图，以及全部目标。 |
| 02 | 初始化最终需要保留的节点集合。 |
| 03 | 逐个处理目标。 |
| 04 | 把该目标自身及其全部生产依赖加入保留集合，多个目标的公共节点自动去重。 |
| 05 | 只输出这些节点及其选中的生产方式，其他候选节点和替代方式不输出。 |
